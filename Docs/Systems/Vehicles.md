# Vehicles (Riding & Driving)

## Current state

TMAX (MINI-066) riding/wheelie/pillion and Range Rover driving/passengers are shipped and long-stable. SuperMoto shipped end-to-end in MINI-119 (mount/ride/wheelie with real hand/foot IK, pillion) and is user-confirmed via real exe play. On top of that: the SuperMoto is now purchasable at the Car Dealer as the "Koss" ($2,500, cheapest vehicle), reusing the exact same wiring as the dev spawn via a shared helper. Auto-mount-on-spawn is off again (dev bike spawn itself stays on for testing). A wheelie back-clip damping fix is shipped but not yet visually confirmed at the exact right value. Full vehicle mounting is currently F for every vehicle - the user has asked for E (mount/enter) + Q (wheelie) instead, not yet implemented.

## Architecture

- `Assets/UpIzUpMini/Scripts/Vehicles/VehicleRider.cs` / `VehicleSeat.cs` (MINI-066) - the shared rider/seat system every two-wheeled vehicle uses. `VehicleRider` handles seated/wheelie pose blending and Humanoid IK; `VehicleSeat` carries PER-VEHICLE baked `seatedOffset`/`seatedPitch`/`wheelieOffset`/`wheeliePitch` (not hardcoded on `VehicleRider` itself, since that's shared across every bike).
- `Assets/UpIzUpMini/Scripts/Vehicles/SuperMotoVehicleInteractable.cs` - the SuperMoto's mount/dismount/pillion interactable, the reference implementation for a vehicle with its own independent input/physics (no throttle/steer relay needed).
- `Assets/UpIzUpMini/Scripts/Vehicles/SuperMotoHandFootLock.cs` - direct bone-override hand/foot IK (`Gadd420.IK`, not Mecanim's built-in `OnAnimatorIK`, which failed twice on this project). Retries every frame until `animator.isHuman` is true, to survive the auto-mount-at-spawn timing race.
- `Assets/UpIzUpMini/Scripts/Vehicles/BikeRiderAnimation.cs` - `UpdateWheelieOverlay(bool)` blends in an authored wheelie pose on the `FullBodyBlend` layer, on top of the position/pitch blend (which alone only translates the body, never reshapes the arms). `WheelieClipWeight` (public property) controls how strongly that authored pose applies - dialed down per-vehicle at Mount() time if needed (see ledger below).
- `Assets/UpIzUpMini/Scripts/Vehicles/VehicleSpawnController.cs` - purchase/spawn/dev-test scaffolding for every vehicle. `WireSuperMotoInstance(instance, player, spawnPos, autoMount)` is the extracted, shared wiring block both the dev spawn path and the real Car Dealer "koss" purchase branch call - written once, not duplicated.
- NPC ragdoll on the vendor's own SuperMoto rider (crash physics) inspired the pattern reused for `Combat.md`'s `NpcRagdoll` - see that file for the actual NPC-combat version.

## What worked / what didn't

- **The "ghost Animator" bug (the single biggest root cause of the whole MINI-119 SuperMoto saga)**: `VehicleRider` had `[RequireComponent(typeof(Animator))]` plus a same-object-only `GetComponent<Animator>()`. Sacat's real Animator lives on a child (`Visual`), not the root - Unity silently auto-created a second, permanently blank Animator on the root, and every hand-IK attempt (Mecanim `OnAnimatorIK`, then a direct bone-override) was talking to the dead ghost. This was misdiagnosed as "Editor batch-mode can't bind an Avatar" FOUR separate times before being properly root-caused from the user's own live Inspector check, not batch tooling. **Prevention**: never assume the Animator is on the same object a script is attached to; use `GetComponentInChildren<Animator>()` and never declare `[RequireComponent(typeof(Animator))]` on a script that might land on an object that doesn't directly carry one.
- **Ragdoll physics and a runtime-built Animation Rigging graph (RigBuilder/TwoBoneIKConstraint) were both tried for hand/foot tracking and abandoned** after recurring, hard-to-reproduce failures - `VehicleRider`/`VehicleSeat` (the proven MINI-066 system) is what actually worked.
- **Mecanim's built-in `OnAnimatorIK` hand IK failed twice** on this exact character/bike despite IK Pass genuinely being enabled. A continuous direct bone-override (`Gadd420.IK`, the vendor's own technique) is what actually works reliably - runs in `LateUpdate`, after the Animator, can't silently under-apply the way Mecanim IK did.
- **(2026-08-28) Patching only `HumanoidAnimationManager.actions`-style per-character data does NOT change what plays** - same lesson as `Combat.md`'s ledger, applies here too since both systems share the same underlying `HumanoidAnimationManager`/shared-controller architecture.
- **(2026-08-28) Wheelie back-clip fix: measured before touching numbers.** User reported "the back goes through the handlebar." `Mini119WheelieBackClipCheck.cs` simulated the seated-vs-wheelie position/pitch math directly and found the chest actually moves AWAY from the handlebar during a wheelie by that math (0.62m -> 0.99m) - the position/pitch numbers were NOT the cause. The real cause was `BikeRiderAnimation`'s authored wheelie-overlay clip (tuned against the TMAX's handlebar geometry, not the SuperMoto's). Fix: dial `WheelieClipWeight` down (0.45 -> 0.22) while mounted on the SuperMoto specifically, cached/restored on Mount()/Dismount() since that component lives on the shared player object (also used by the TMAX) - can't be a permanent change.
- **(2026-08-28) Pillion boarding as a one-shot check at Mount() time did NOT work with auto-mount.** The original TMAX pattern (`BikeInteractable.BoardPillion`) only works because the player always walks up and presses F first, giving the passenger time to catch up. An instantly-auto-mounted bike breaks that assumption. Fixed by checking every `Update()` instead of once at Mount() time.
- **(2026-08-24) Two torque-based attempts at a continuous roll-corrector (`SuperMotoUprightAssist`) were built and rejected after real testing** - one resonated into a violent tumble, one was too weak and let the lean creep. Replaced with a kinematic `MoveRotation`-based approach (same technique already proven for the wheelie) - no torque, no gain to tune, cannot resonate.
- **A self-reinforcing stuck-pitch bug**: measuring pitch via `Mathf.Asin(forward.y)` (fold-back-prone past 90deg) and baking that measurement directly into the real rotation every frame turned one bad reading into a permanent stuck pose. Fixed by using a signed angle around the flattened-forward-derived right axis instead.
- **Real Editor batch-mode verification repeatedly disagreed with actual gameplay** across this whole task (the `Input_Manager` destroy-order bug and a world-axis `FreezeRotationZ` constraint bug were both invisible to batch tests, only found from the user's own `Player.log` or direct play feedback). Batch-mode checks are still valuable for catching what they CAN catch (see the many `Mini119*.cs` tools), but a final "works in real gameplay" sign-off from the user remains necessary before calling a vehicle feature done.

## What worked / what didn't (continued)

- **(2026-08-29) Dev diagnostic HUD/tuner overlays left wired into the real mount flow, not just a test path, is a real ship-quality risk.** `SuperMotoWheelieHud` (an always-visible on-screen wheelie diagnostic) and `Mini119StockDemoBikeTuner` (a T-toggle live-tuning slider panel) were both added inside `WireSuperMotoInstance` - the SAME shared helper the real Car Dealer "koss" purchase uses, not a dev-only branch - so every real player who bought/mounted the Koss would see this debug UI. User: "remove the wheelie and bike stuff on the screen." Removed both `AddComponent` calls from `WireSuperMotoInstance`; the component scripts themselves are kept (not deleted) in case a future wheelie regression needs the same diagnostic again. The TMAX's own equivalent tuner (`TmaxWheelieTuner`, baked by `Mini065TmaxPhysicsTest.cs`) was already correctly gated off via `IncludeDevTuner = false` since MINI-080 - confirmed, not assumed, before concluding no further action was needed there.

## Open items

- **E for mount/enter vehicles, Q for wheelie** - requested, not yet implemented. Currently F mounts every vehicle and E is the SuperMoto's own wheelie key (remapped from the vendor's default LeftCtrl). Needs care: F is ALSO the melee Attack key (`Vehicles.BikeInteractable.ConsumedMountKeyThisFrame` guards against punching on the same frame you mount) - an equivalent guard will be needed wherever E's dual use (mount vs. wheelie-while-mounted) could otherwise collide, though since mount only fires while NOT already mounted and wheelie only fires while mounted, there should be no runtime overlap.
- Wheelie-overlay damping (0.22 weight) is shipped but the exact right number still needs the user's visual confirmation.
- Riding/driving as a fully "data-driven system" (a real per-vehicle definition table, the way `Combat.md`'s `MeleeMoveLibrary` now works) has NOT been built - `VehicleSeat` is already close to this in spirit (per-vehicle baked pose data), but `VehicleSpawnController`'s purchase/spawn logic is still mostly per-vehicle branches (`if (itemId == "koss")`, `if (itemId == "range_rova")`, ...), not a single generic table. Worth revisiting if a third/fourth vehicle is added.
- TMAX production repair (see `Docs/CLAUDE-HANDOFF-CURRENT.md` section 6, MINI-116-era): TMAX can look see-through and its build payload is large - not yet diagnosed.
